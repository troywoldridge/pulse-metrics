# Pulse Metrics — Phase 2E3C5D9: enrollment migration candidate

**Status:** Review-only, NOT applied to any existing/customer database
**Reviewed baseline:** `2afc6d35019aef5288d19a184ff16144e5b05b31`
**Public launch:** NO-GO
**Purpose:** Prove migration and production-intent adapter behavior against an isolated PostgreSQL installation.

## Security boundaries

- Existing immutable Drizzle baseline and the six recorded administrator SQL sources remain unchanged.
- The new migration is **separately versioned** as `scripts/agent-enrollment/migrations/0001_agent_enrollment.sql` because the original six-step manifest explicitly forbids unreviewed seventh administrator scripts.
- No migration or API is deployed. `server.ts`, browser entry, WorkOS middleware and database credentials are unchanged. There is no public agent enrollment or ingest endpoint.
- A migration version receipt (`pulse_agent_enrollment.schema_migrations`) and the five functions are created atomically within one SQL transaction. The receipt table has forced RLS and no runtime table grants.
- A NOLOGIN, NOINHERIT, BYPASSRLS executor owns only the five fixed SECURITY DEFINER functions. It receives column-limited grants, is not a member of any login role and must not acquire other membership or table privileges.
- The runtime role remains unable to select/insert/update agent credential and enrollment token tables directly. It can invoke only fixed functions in the dedicated schema.
- Issuance independently verifies the verified WorkOS subject and organization owner/admin role **inside PostgreSQL**. Redemption uses a token digest, not a requested organization. A row lock prevents concurrent double redemption. No raw secret is stored in PostgreSQL.
- Verification binds credentials to an agent and its organization and rejects expired/revoked credentials; rotation and revocation require authorized organization membership and maintain audit records.
- Every raw secret is generated by Node's cryptographic RNG and transmitted only by an explicitly approved future authenticated transport. The migration candidate does **not** provide TLS, enrollment abuse controls, session verification or on-host secret storage.
- An injected Drizzle SQL executor is required for the adapter; merely importing the adapter does not connect to PostgreSQL or mount routes.

## Release and migration gates

1. Verify the SQL checksum with `node scripts/agent-enrollment/verify-candidate.mjs`. The check is read-only and pins exact source bytes plus the reviewed application baseline.
2. `bash scripts/test-agent-enrollment-migration-rehearsal.sh` builds a brand-new, marked, Unix-socket-only PostgreSQL cluster using the existing independent replay process and six historical privileged migrations.
3. Only after confirming the isolated connection, roles, ledger and original DB catalog fingerprint does the rehearsal apply the **candidate SQL** on the disposable cluster.
4. Two synthetic organizations and owners, a viewer, expired/revoked tokens and concurrent redemption exercise authorization, denial, credential rotation and revocation. HTTP issue/redemption are tested using injected production-intent SQL adapters, with only a loopback synthetic-identity test server.
5. The script confirms the restricted role cannot read the new receipt or protected credential tables, confirms the five function owners/search paths, preserves the historic migration ledger, rechecks the original developer catalog read-only, then removes its own marked cluster.
6. Test success is **not** permission to apply the SQL to a working, staging or production database. A separate release review must address operator authorization, signed/immutable plans, privilege preflight, independent approval, backup, deployment idempotency and crash/reconciliation procedures. Do not add this candidate to the existing six-step release manifest without a new explicit compatibility and baseline decision.

## Not yet implemented

- Deployment mechanism with authorization, locking, independent migration reconciliation and recovery.
- Real TLS edge, pre-auth network rate limiting, per-actor quotas and secure machine credential delivery/storage.
- Public organization enrollment routes, public agent token redemption, authenticated machine telemetry ingestion, dashboard reads and WebSocket authorization.
- Production tests of deployment networking, container/systemd hardening, rotation grace-period policy, machine key custody, replay handling and retention.

**Rollbacks:** Do not `DROP` production functions or tables after use, since enrolled agents and valid credentials are durable identities. Prefer a separately reviewed forward migration and recovery plan. The isolated rehearsal can destroy its **own marked disposable** database only; it never alters the original development database.
